# TODO: future features

Features to add after the core hub works and has replaced Notifiarr. Each one has a short scope and a prompt you can paste into Claude Code in VS Code.

## How to use

1. Pick an item and create a branch named `feature/<name>`.
2. Start a new Claude Code session in the repo.
3. Paste the item's prompt. It already tells Claude to follow the ground rules below.
4. Review the diff, run the tests, merge, and tick the box.

Dependencies are noted per item; do those first.

## Ground rules (apply to every prompt)

- Read `CLAUDE.md`, `PLAN.md`, and `README.md` before starting.
- One feature per branch, in small commits.
- Database changes only through a new numbered migration.
- Settings live in the UI and the database; add an environment variable only if there is no alternative.
- Add tests, with fixtures wherever payloads are involved.
- Never log or store secrets; run stored payloads through the redaction function.
- Code comments are concise and describe only what the code does.
- Update the matching section of `README.md` if setup or user-facing behavior changes.
- Stop when the done-when condition is met, and list what changed.

## 1. Heartbeat monitoring

- [ ] Alert when a source that should report on a schedule goes silent.

**Scope**

- New `heartbeats` table: source id, optional check key, expected interval, grace period, last seen, state.
- Ingest updates last seen whenever a matching message arrives.
- The self-check loop marks a heartbeat late after interval plus grace, sends an error through the normal pipeline as source `hub`, and sends a recovery message when the source reports again.
- UI: a Heartbeat section on the source page, and a dashboard badge listing late sources.

**Done when:** a source with a 5-minute heartbeat that stops sending produces one error after interval plus grace, and one recovery when it resumes.

```text
Follow the ground rules in TODO.md. Add heartbeat monitoring: a heartbeats table
(source id, optional check key, interval, grace, last seen, state), last-seen
updates in the ingest path, late and recovery messages generated by the
self-check loop through the normal pipeline, and a Heartbeat section on the
source page plus a dashboard badge. Include tests for late, still-late (no
repeat alerts), and recovery.
```

## 2. Mute and snooze

- [ ] Silence a source, route, or event type for a set time.

**Scope**

- New `mutes` table: scope (source, route, or event type), target id, until, reason.
- The pipeline checks active mutes before queueing; muted messages are stored with status `muted` and still appear in the log.
- Option to keep delivering errors while muted.
- UI: Mute buttons (1 hour, 8 hours, 24 hours, custom) on source and route rows, and a Muted page listing active mutes; mutes expire automatically.

**Done when:** a muted source's messages are logged as muted and not posted, and posting resumes at expiry.

```text
Follow the ground rules in TODO.md. Add mute and snooze: a mutes table, a
pipeline check before queueing that records status muted, an option to still
deliver errors, mute buttons on the sources and routing pages, a Muted page,
and automatic expiry. Include tests for expiry and the keep-errors option.
```

## 3. Grouping and digests

- [ ] Merge bursts into one message, with an optional daily summary.

**Scope**

- Per-source settings: grouping window (seconds), group key (for example series name), and maximum items.
- Messages with the same key inside the window are held, then sent as one embed listing the items; the first Discord message is edited as new items arrive, up to the maximum.
- Optional daily digest: a scheduled job posts counts and highlights per source.
- Held messages stay in the log with status `grouped` and a link to the group.

**Done when:** 20 Sonarr import events within 30 seconds produce one embed.

```text
Follow the ground rules in TODO.md. Add grouping: per-source window, group key,
and max items; hold matching messages in the queue and send one combined embed,
editing it as items arrive; mark held messages as grouped and link them to the
group in the message detail page. Add an optional daily digest job. Test with a
burst of 20 Sonarr fixtures.
```

## 4. Phone push for critical alerts

- [ ] Send selected alerts to your phone as well as Discord.

**Scope**

- Introduce an `outputs` table: id, type (`discord`, `ntfy`, `pushover`), encrypted config.
- Routes pick one or more outputs and a minimum severity per output.
- Build the `ntfy` and `pushover` senders, each with a test button.
- `deliveries` records which output each attempt used; failures show in the log.

**Done when:** an error-level message appears in Discord and as a phone notification, and a failing output does not block the other.

```text
Follow the ground rules in TODO.md. Add an outputs abstraction and two new
outputs, ntfy and Pushover. Add the outputs table (encrypted config), per-route
output selection with a minimum severity, an output_id column on deliveries,
and a Test button on the outputs page. Keep Discord delivery behavior unchanged.
Test that one failing output does not block another.
```

## 5. Deduplication

- [ ] Collapse identical repeated alerts into one message with a count.

**Scope**

- Fingerprint is source plus the message `key`, or a hash of title and body when there is no key.
- Within a window (default 10 minutes) repeats are not sent; the original embed is edited to show a count, for example "x3 in the last 10 min".
- Suppressed repeats are logged with status `suppressed`.
- Per-source on/off and window setting in the UI.

**Done when:** the same error sent five times in a minute posts once and shows a count of 5.

```text
Follow the ground rules in TODO.md. Add deduplication: a fingerprint from source
plus key (or hash of title and body), a per-source window, suppression of
repeats with status suppressed, and editing the original Discord message to
show a repeat count. Add the settings to the source page. Test the window
boundary and the count edit.
```

## 6. Quiet hours and severity rules

- [ ] Hold low-priority messages at set times, and mention roles on critical ones.

**Scope**

- Route-level schedule: days, start and end time, timezone.
- Action during quiet hours: hold, drop, or downgrade; held messages are released as one digest when quiet hours end.
- Errors can be set to always deliver.
- Per-severity role or user mentions, chosen from the bot's synced roles.

**Done when:** info messages sent overnight arrive as one digest in the morning, while an error posts immediately and mentions the chosen role.

```text
Follow the ground rules in TODO.md. Add quiet hours to routes: schedule,
timezone, action (hold, drop, downgrade), always-deliver errors, and a release
digest. Add per-severity role and user mentions, using roles synced by the bot.
Test the schedule logic across midnight and a daylight saving change.
```

## 7. Slash commands and buttons

- [ ] Control the hub from Discord. Depends on item 2.

**Scope**

- Register guild slash commands on start: `/status` (health checks, queue depth, last message per source), `/last <source> [count]`, `/mute <source> <duration>`, `/unmute <source>`, `/resend <id>`.
- Limit commands to a configured admin role; replies are ephemeral.
- A small button framework with a typed `customId` format, used first for Retry and Mute 1h buttons on error messages.
- Interactions go through the bot module, which calls the backend API only.

**Done when:** `/status` shows live data, and the Mute 1h button on an alert creates a mute.

```text
Follow the ground rules in TODO.md. Add Discord slash commands (/status, /last,
/mute, /unmute, /resend) restricted to an admin role, with ephemeral replies, and
a button framework with a typed customId. Add Retry and Mute 1h buttons to error
embeds. The bot must call the backend through its API only. Test with mocked
interactions.
```

## 8. Status message updated in place

- [ ] Keep one message per host or service that shows its current state.

**Scope**

- Sources can declare a `statusKey`; the hub keeps one Discord message per channel and key and edits it instead of posting a new one.
- New `status_messages` table: channel id, key, Discord message id, content hash.
- If the message was deleted or the edit fails, post a new one and store the new id.
- UI: choose which sources use status messages and which channel they live in.

**Done when:** repeated health-check results update a single message per host, and deleting that message causes a new one to appear on the next result.

```text
Follow the ground rules in TODO.md. Add status messages: a statusKey on standard
messages, a status_messages table, edit-in-place delivery with a fallback to a
new message when the edit fails, and UI to enable it per source. Update the
health-check adapter to set statusKey to the host. Test the deleted-message
fallback.
```

## 9. Acknowledge and escalate

- [ ] Track unacknowledged errors and re-alert. Depends on item 7.

**Scope**

- New `incidents` table: key, opened at, acknowledged by and at, escalation count, closed at.
- An Ack button on error messages and an `/ack` command.
- Per-route escalation: after N minutes unacknowledged, repost with a role mention, up to M times.
- A recovery message closes the incident automatically.

**Done when:** an unacknowledged error reposts with the role mention after the set time, and pressing Ack stops further reposts.

```text
Follow the ground rules in TODO.md. Add incidents: an incidents table opened by
error messages that carry a key, an Ack button and /ack command, per-route
escalation (after N minutes, repost with a role mention, at most M times), and
auto-close on recovery. Use the existing button framework. Test escalation
timing with a fake clock.
```

## 10. Multiple outputs and forwarding

- [ ] Send one message to several destinations. Depends on item 4.

**Scope**

- Add `webhook` and `email` (SMTP) output types alongside Discord, ntfy, and Pushover.
- The webhook output posts the standard message or a template-rendered body, with custom headers.
- Each output has its own retry and status in `deliveries`.
- Loop protection: outgoing webhooks carry an `X-Notify-Hub-Origin` header, and ingest drops messages that carry it.

**Done when:** one source can post to Discord and forward to another webhook, and a forwarded message sent back to the hub is dropped.

```text
Follow the ground rules in TODO.md. Using the outputs abstraction, add webhook
and SMTP email outputs with per-output retries, optional template bodies, and
loop protection through an X-Notify-Hub-Origin header that ingest rejects. Add
UI for configuring both. Test the loop case.
```

**Scope**

- Live preview on the Formatting page using a saved sample.
- Safe fallbacks: a template error falls back to the default render and logs the error.

**Done when:** changing a template changes the embed for the next message, and a broken template never blocks delivery.

```text
Follow the ground rules in TODO.md. Add Handlebars templates for title, body,
and fields on sources and routes, with route templates taking priority, a live

template error. Disable helpers that could run code. Test the fallback.
```

## 17. Users, roles, and audit log

- [ ] Several logins, with a record of who changed what.

**Scope**

- `users` table with Argon2 password hashes and roles `admin` and `viewer`; viewers see logs but cannot edit, and raw payloads are hidden from them.
- `audit_log` table recording config changes with before and after values (redacted).
- Optional mapping from a Cloudflare Access email to a user.
- Migration that turns the existing admin account into the first admin user.

**Done when:** a viewer can read the log but every edit endpoint refuses them, and every config change appears in the audit page.

```text
Follow the ground rules in TODO.md. Add multi-user support: a users table with
Argon2 hashes and admin and viewer roles, role checks on every admin API route,
hidden raw payloads for viewers, an audit_log table with redacted before and
after values, an Audit page, and an optional Cloudflare Access email to user
mapping. Migrate the existing admin. Test authorization on every route.
```
