Phase 3 (sources and routing) is built. Sources, routing rules, the fallback and alert channels, the discarded log and every setting are now managed in the web UI, and the seed script is gone.

## Summary

- **Phase 3:** done. The done-when condition is met: no seed script is needed, and every setting that exists is changed through the UI.
- **Pages:** Dashboard (the new home page), Sources, Routing, Muted, Discarded and Settings.
- **Extras after the audit:** a webhook address setting, resend, drop rules, rule mentions, mute and snooze (TODO item 2), testing unsaved rules, and address blocks kept across restarts.
- **Security items from `CLAUDE.md`:** all Phase 3 items are done. The discarded log has a retention, a row cap, address blocking and a spike alert; `npm run seed` is removed; a rotated token works for 10 minutes only; changing the password asks for the current one and ends every other session.

## Decisions

- **Embed fields:** at most 25, Discord's own limit. PLAN.md section 6 and the README now say 25 instead of 10.
- **Showing a source URL again:** a single `POST /api/sources/:id/url` returns the URL with the token, sent with `Cache-Control: no-store`. No other response contains a source token; setup no longer returns one either. `CLAUDE.md` names this as the one exception to the secrets rule.
- **Routing model:**
  - One ordered list of rules. Each rule applies to one source or to any source.
  - The first match stops the search, unless the rule has "Also check later rules" turned on.
  - A message goes to each channel once.
- **Alert channel:** a new setting. The discard spike alert uses it now, and the Phase 7 self-checks will use it too.
- **Settings page:** every setting from the plan is on it. Two don't work yet and are labeled "Not active yet":
  - Message retention: the cleanup job comes in Phase 7.
  - Export and import: also Phase 7.
  - The body size limit does work, and applies after a restart.
- **Blocking defaults:**
  - Blocking: 20 bad requests in 10 minutes block an address for 15 minutes.
  - Exempt ranges: none by default.
  - Scope: a block covers every webhook from that address, including valid ones.
  - Discarded log: 7 days and at most 10,000 rows.
  - Spike alert: at 50 discards in 10 minutes.
- **Webhook URL host:** built from the browser's address. Through the tunnel that would be the tunnel hostname; a "LAN address" setting can come with Phase 6.
- **Outside Phase 3, approved:** a minimal `GET /api/adapters` and an optional `help` field on adapters, so the Sources page can offer types and setup help. Phase 4 extends both.
- **Admin API body limit:** fixed at 1 MB. The webhook body limit setting applies only to `/hook`, so raising it never raises the admin API's.

## What was built

**Sources**

- **Add a source:** pick a type and a name; the id is suggested from the name, and the hub generates the token.
- **On and off:** a switch on every row of the source list, and an "Accept webhooks" switch under Status in the source panel. The first version had only a switch labeled "On: webhooks are accepted", which was easy to miss.
- **Source panel:** rename, Copy URL and Show (both fetch the URL only on click), test-send, rotate, delete, and the adapter's setup help.
- **Rotation:** the old token keeps working for 10 minutes, and the page shows until when. After that it is logged as the new reason `expired token`. Rotating twice ends the oldest token at once.
- **Off and delete:**
  - A source that is off discards its webhooks, and its test button is refused.
  - Deleting a source removes the rules made only for it. Its messages stay in the log.

**Routing**

- **Rules:** a priority list with drag-to-reorder, plus arrow buttons for phones and keyboards.
- **Conditions:**
  - Events: a list, matched without case.
  - Severities: a list.
  - Text contains: searched in the title, body and fields.
- **Reordering:** the server accepts only the full current list of rule ids, so a list changed in another tab isn't reordered blindly.
- **Rule tester:** runs a typed message, or one loaded from the log, through the saved rules. It shows where the message would go and why each rule did or did not match.
- **Fallback channel:** set on the Routing or Settings page. Deliveries record whether they went to the fallback, and the log marks them.

**Discarded log and protection**

- **Discarded page:**
  - Filters by source, address and reason, with paging.
  - Links to the source that was tried, Clear, a "Blocked now" list with Unblock, and all the settings.
- **Blocking:** a blocked address gets 429 with `Retry-After` and is not logged. The tracker holds at most 10,000 addresses and counts in one-minute buckets, so memory stays bounded.
- **Never block:** a list of addresses and ranges (IPv4, IPv6, or IPv4-mapped), checked again on the server.
- **Spike alert:** posted to the alert channel at most once per 10 minutes, as a message from the hub itself (source `hub`, shown as Notify Hub). Sender-chosen text in it is shown as inline code, so it cannot form links.
- **Size limits:**
  - Pruning: hourly, and at once when the settings change.
  - Row cap: enforced on every insert.
  - Sender-chosen text: user agent and content type are cut to 300 and 200 characters.
- **Dashboard counter:** "discarded today" comes from a new hourly count table, because the log groups repeats from one sender into one row. The nav bar shows the same count.

**Settings, dashboard and the rest**

- **Settings page:** Discord connection (reuses the setup step), Sync channels, alert and fallback channels, message retention, body limit, password change, export and import (not active yet), and the version.
- **Dashboard:** messages, failures, unrouted messages and discards since local midnight, plus queue depth, bot status, and per-source counts with the last message time.
- **Database:** migration `0002_routing`:
  - Rebuilds `routes`: `source_id` may be empty, and new columns `name` and `continue_matching`.
  - Adds `route_id` and `fallback` to `deliveries`.
  - Creates `discard_counts`.

  Settings are stored as two JSON rows (`hub.settings` and `discarded.settings`). A field that is missing or invalid falls back to its default.
- **Seed script:** `server/src/seed.ts`, the `npm run seed` script and its README line are removed.

## Problems solved

- **drizzle-kit migration:**
  - The generated copy step for the rebuilt `routes` table read the new `name` and `continue_matching` columns from the old table, which doesn't have them.
  - Fixed by hand to copy only the old columns.
  - Checked against a database with Phase 2 data.
- **Fallback deliveries:** an empty rule id was going to mean "fallback", but Phase 1 and 2 deliveries and hub alerts also have no rule. An explicit `fallback` column avoids mislabeling them.
- **CSP console error:**
  - The new pages imported two values from `shared` at runtime, which pulled Zod into the browser bundle.
  - Zod's startup check for `eval` support was blocked by the Content-Security-Policy, which then logged an error.
  - `slugify` moved to `web/src/lib/format.ts` and the reason list became a typed constant. The web code again uses only type imports from `shared`, the CSP stays strict, and the bundle-size warning is gone too.
- **Phone layout:** on the Routing page, rule names were squeezed to one letter. They now keep a minimum width, and the buttons wrap below.

## Security review

Checked against the `CLAUDE.md` Security section before committing.

- **Admin API:** every new route needs a session; a test checks all 22 for a 401. Bodies, queries and path parameters go through shared Zod schemas with `parseWith`.
- **Source tokens:**
  - Stored only through the `SecretBox`, and compared with `tokensMatch`, including the previous token.
  - Only `/url` returns one.
  - Tests check the token is absent from every other response, from the database, and from the logs at trace level.
  - A request from another site to `/url` gets 403.
- **Logging:** the three new log lines hold only counts. The spike alert holds addresses and source ids, never token hints.
- **Ingest:**
  - The blocked check and the token check run before the body is read.
  - Blocked and rejected requests store nothing in `messages`.
  - Hub alerts go through the redactor like every other stored payload.
- **Browser:** no CORS headers, no `dangerouslySetInnerHTML`, no new external links, CSP unchanged. URL responses stay out of TanStack's mutation cache (`gcTime: 0`).
- **Queries:** Drizzle parameters throughout. Filter text in LIKE patterns is escaped (`contains()`), and a test checks that `%` is matched literally.
- **Password change:** wrong current passwords count toward the login lockout.

## Second audit

A full read-through of the Phase 3 code after manual testing.

**Found and fixed**

- **Link injection into the alert channel:**
  - The source id in a webhook URL is decoded, so `%0A` becomes a real line break, and it is stored as the source tried.
  - In the spike alert, that line break ended the inline code span, so a LAN sender could post a clickable markdown link to the alert channel without any token.
  - `asCode` now turns line breaks and other control characters into spaces.
  - A test sends exactly that request; it was checked to fail without the fix.
- **Spike alert senders:** the alert listed the five newest senders instead of the busiest. It now sorts by repeat count.
- **Settings stored as non-objects:** a settings row holding `null`, an array or text would have crashed every settings read, including ingest. It now falls back to the defaults.
- **Live log filter:** has a "Notify Hub (alerts)" choice, so the hub's own alerts can be found.

**Added**

- **`server/test/migrations.test.ts`:** migrates a database at `0001` with Phase 2 rows to `0002`, and checks the routes and deliveries kept, the new columns filled, and the foreign keys intact.

# Phase 4 (in progress)

On branch `phase-4`, nothing committed yet. The adapter system is built; the Sonarr, Radarr and Prowlarr adapters wait for real payloads captured from those apps, which needs the user's server to be back up.

## Done

- **Adapter file format** (PLAN.md section 7) with the declarative `map` alternative, checked against a Zod schema on load. Unknown keys are refused, so typos show as errors.
- **`adapters/_template.js`:** commented, with one working sample; copied into `$DATA_DIR/adapters` on first start, never overwritten. The release workflow now ships the `adapters/` folder.
- **Loader** (`server/src/adapters/loader.ts`):
  - esbuild bundles each file; only imports inside the adapters folder are allowed.
  - Syntax errors give the file, line and column; run-time errors are mapped back through the source map, such as `boom (demo.js:6:11)`.
  - Hot reload with `fs.watch`; a broken change keeps the last working version running.
  - Files starting with `_` are not loaded but can be imported as helpers.
  - Every load runs the samples; failing samples give the status `samples-failing`.
- **Built-in standard adapter** moved to `server/src/adapters/builtin/standard.ts`, same format as user files.
- **Worker isolation** (the Phase 4 item in `CLAUDE.md`):
  - One worker thread for all adapters, started from a `data:` URL with an empty environment and no `execArgv`.
  - Each adapter runs in its own V8 context (`vm.constants.DONT_CONTEXTIFY`) that holds only the JavaScript built-ins: no `process`, `require`, `import()`, timers, `URL`, or network. `console` is a no-op, so adapters cannot log payloads.
  - A strict-mode bridge inside each context keeps its own copies of the built-ins it uses and passes only strings to the worker.
  - Limits: 5 s per call and 64 MB of heap. Running over stops the worker; it restarts with every adapter loaded again.
  - `fetch:<host>` permissions are approved per adapter on the Adapters page and stored in the existing `adapters` table. The check runs in the worker's realm, which adapters cannot reach. Approved fetch reaches only those hosts, refuses redirects, and reads at most 1 MB.
- **Pipeline:** `process` is async and waits for the adapters to load.
- **API:** `GET /api/adapters` returns `{ folder, adapters, failed }`; new `POST /api/adapters/:id/run-samples` and `PUT /api/adapters/:id/permissions`. Source detail has `adapterProblem`.
- **UI:** Adapters page, a warning on the source page, and a Copy body button in the message's Raw tab.
- **Migrations:** none.
- **Tests:** 215, all passing (178 before). Typecheck, lint, format and build clean. The compiled build was checked in headless Edge on port 18080 at desktop and phone width.

## Security review

Checked against the `CLAUDE.md` Security section before committing.

- **Found and fixed:** the first version ran every adapter in the worker's own realm, with dangerous globals removed. Because they shared built-ins, an adapter that requested `fetch:<host>` could replace `Array.prototype.includes` or `some`, which the worker's permission check used, and get `fetch` without approval, for any host. Adapters now run in separate contexts and only strings cross over. Tests cover a meddling adapter, the `constructor` and `caller` escapes, and an adapter that breaks its own `JSON` and `Promise`.
- **Admin API:** the three adapter routes need a session and are in the 401 test; params and bodies go through shared Zod schemas with `parseWith`. Approvals accept only permissions the file asks for.
- **Secrets:** none are handled by the new code. The worker has an empty environment; a test sets a variable in the main process and checks adapters cannot see `process` at all.
- **Logging:** the new log lines hold file names, adapter ids, statuses and folder errors only. Adapter `console` output is discarded.
- **Ingest:** unchanged. Adapters receive the stored, redacted payload; the test button's sample headers go through the same redaction in `ingest.accept`.
- **Browser:** no CORS headers, no `dangerouslySetInnerHTML`, CSP unchanged. Sample embeds go through `renderEmbed`, which keeps only http(s) links.
- **Queries:** the new adapter state and approval writes use Drizzle.
- **Outbound requests:** only to hosts an adapter's approved permissions allow.
- **Accepted:** the adapters folder is trusted. A symlink placed there as an import target is followed by esbuild; whoever can write to the folder already controls the adapters. Approvals are kept per adapter id, so a new file with the same id and the same requested host keeps the approval.
- **For Phase 6:** per-source adapter config may hold secrets; an adapter that puts config values in an error message would have them stored in the message log.

## Decisions

- Each adapter runs in its own context, inside one shared worker.
- Fetch permissions are scoped per host (`fetch:api.example.com`), not a bare `fetch`.
- One shared worker, not one per adapter, to save memory on the 512 MB LXC; separate contexts give the isolation.
- An adapter whose samples fail stays active, with a warning.
- Adapter `style` is validated now and applied with the Phase 6 style editor.
- "Save the last payload as a sample" moves to Phase 6.
- The Adapters page polls every 3 s instead of using the SSE stream.
- In a `map`, an optional part whose placeholders are all empty is left out.
