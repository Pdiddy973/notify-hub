## Phase 1: Core pipeline

- **Database:** all 11 tables from the plan, created by the first migration in `server/migrations/`. Migrations run when the hub starts, and the bot token and source tokens are stored encrypted.
- **Webhooks:** `POST /hook/<source>/<token>`, or the token in an `X-Hub-Token` header.
  - The token is checked before the request body is read.
  - A wrong token gets the same 404 as an unknown address and is logged in the discarded table with only a hint of the token.
  - Passwords and API keys in a payload are hidden before it's stored.
- **Message format:** color by severity, the source name at the top and the event type at the bottom. Text is cut to Discord's limits with an ellipsis.
- **Bot:**
  - Logs in, saves the server's text channels, and sends messages in order.
  - Messages wait in the queue while the bot is offline.
  - After a restart, unfinished work is picked up again.
- **Adapter errors:** if an adapter can't read a payload, an error embed is sent instead and the raw payload is kept.
- **Seed script:** `npm run seed` saves the bot token, server, one test source and one route. It's temporary until the Phase 2 setup page. It checks the bot token's format, and prints test commands for curl and PowerShell.

## Problems solved

- **"An invalid token was provided":** the seed was first given the Application ID, then the Public Key. The bot token is on the Bot page, under Reset Token. The seed script now detects both mistakes.
- **curl sent nothing:** in the VS Code PowerShell terminal, `curl` is PowerShell's own web command, which doesn't accept curl's options. Use `Invoke-RestMethod`, or run curl from Command Prompt or Git Bash.

## Security audit

A full review of login, sessions, secrets, ingest, logging and the web UI, before committing Phase 2.

**Found and fixed**
- **Setup takeover:** before the admin account existed, anyone on the LAN, or a website using DNS rebinding, could create it. Setup now needs a one-time code that the hub prints in its log (and the installer prints at the end).
  - Wrong codes count toward the same lockout as failed logins.
  - The code stops working once the admin exists.
- **Redaction gaps:** fields such as `client_secret`, `refresh_token`, `botToken`, `webhookPassword`, `passwd` and `privateKey` were stored in plain text. Any header or field whose name *contains* a secret word is now masked.
- **Malformed Origin:** an `Origin: null` or malformed header caused a 500 error. It now gets a 403.
- **Login lockout memory:** the lockout tracker could grow without limit under a spray from many addresses. It now tracks at most 1,000 addresses.
- **systemd unit:** now has `UMask=0027` (the database isn't world-readable) and `ProtectHome=true`.

**Checked and fine**
- **Git history:** no secrets ever committed; `.env`, `data/` and build output are ignored.
- **Secrets at rest:** the bot token and source tokens are encrypted with AES-256-GCM. The password is stored as an Argon2id hash, and sessions only as hashes. None of them is ever returned by the API or written to the logs.
- **Browser protections:** SameSite=Strict cookies, the same-origin check, no CORS headers, a strict Content-Security-Policy, and no HTML injection or `eval`.
- **Database queries:** all parameterized, with LIKE patterns escaped.
- **Public routes:** only four (session, setup account, login and logout). Everything else returns 401 without a session.

**Rules and open items** are now in the Security section of `CLAUDE.md`, with each open item tied to the phase that fixes it.
